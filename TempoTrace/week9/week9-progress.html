TempoTrace

8주차는 시험 기간이어서 진행하지 않았고, 7주차 발표에서 받은 피드백 3가지를 반영한 내용을 보고합니다.

기준값을 바꾸면 결과 추이까지 바로 바뀌고, 바꾼 값이 기본값이 되며, 기록은 몇 번을 실행해도 빠짐없이 누적되도록 개선했습니다.
01. 7주차 피드백

교수님 피드백 3가지

①
허용 오차 범위를 바꾸면, 바꾼 값이 기본값이 되고 결과 추이도 함께 바뀌도록 수정7주차: 기준을 바꿔도 연습 기록(추이)은 그대로였음
②
10,000번 실행해도 json에 데이터가 누적되는지 확인7주차: 기록 개수에 제한이 있었고, 많이 쌓였을 때의 동작을 검증하지 않았음
③
기준값(150ms)을 페이지 안에서 바로 바꾸고, 바뀐 결과가 즉시 나타나도록 구현7주차: 슬라이더는 있었지만 현재 연주 결과만 바뀌었음
02. 반영 요약

무엇이 문제였고, 무엇을 바꿨나

기존 문제이번에 한 것
피드백 ①연습 기록에는 "그날의 정확도 숫자"만 저장되어, 기준을 바꿔도 과거 회차는 바꿀 수 없었음기록마다 onset 원본을 함께 저장하고, 기준이 바뀌면 모든 회차를 다시 채점. 바꾼 값은 기본값으로 저장
피드백 ②기록이 100개를 넘으면 오래된 것부터 삭제됨. 저장할 때마다 파일 전체를 다시 씀개수 제한을 없애고 한 줄씩 덧붙이는 방식으로 변경. 10,000회 반복 실행 검증 스크립트 추가
피드백 ③슬라이더만 있었고, 바꿔도 연습 기록·표는 그대로였음슬라이더 + 숫자 직접 입력 + ±5 버튼. 바꾸는 즉시 페이지 전체가 다시 계산됨
03. 피드백 ③ 페이지 안에서 기준값 변경

바꾸는 즉시 모든 결과가 바뀜

  • 기준값을 슬라이더 / 숫자 직접 입력 / ±5 버튼으로 조정 숫자 입력은 10~1000ms, 범위를 벗어나면 자동 보정
  • 바꾸는 즉시 아래가 모두 한꺼번에 갱신 정확도 · 평균 오차 · 놓친/엉뚱한 음 · 시간대별 분포 · 연습 기록 추이 · 표 · 자주 틀리는 구간
  • 슬라이더를 빠르게 끌어도 부드럽도록, 화면 갱신은 한 프레임에 한 번만 수행
기준값 조정 영역 — 슬라이더, 숫자 입력, ±5 버튼, 되돌리기, 저장 안내
04. 피드백 ① 기준값 변경 → 결과 추이 변경

같은 기록인데 기준에 따라 추이가 달라짐

  • 기록에 onset 원본이 들어 있어서, 기준을 바꾸면 모든 회차를 새 기준으로 다시 채점하여 추이·표·구간 분포를 갱신
  • 표에는 '기록 당시 기준'을 함께 남겨서, 지금 기준과 어떻게 다른지 확인 가능
기준 50ms (엄격하게)
기준 250ms (관대하게)
05. 피드백 ① 바꾼 값이 기본값이 되는 구조

페이지에서 바꾼 값이 다음 실행에도 유지됨

python accuracy_test.py연주 분석
→
practice_history.json기록 누적 (onset 원본 포함)
→
리포트 서버127.0.0.1 (내 컴퓨터 안)
→
브라우저 리포트기준값 변경 → 즉시 재계산
↩ 바꾼 기준값 → tempotrace_settings.json 에 저장 → 다음 실행의 기본값
# 분석 + 리포트 서버 실행 (종료: Ctrl+C)
python accuracy_test.py
# 기본 기준값을 터미널에서 직접 바꾸기
python accuracy_test.py --tolerance=200
# 서버 없이 파일로만 열기
python accuracy_test.py --no-serve
  • 웹페이지는 컴퓨터의 파일을 직접 바꿀 수 없어서, 작은 로컬 서버가 값을 받아 설정 파일에 저장 (내 컴퓨터에서만 접속 가능)
06. 피드백 ② 10,000번 실행 검증

기록이 빠짐없이 누적되는지 확인

  • 기록 개수 제한을 없애고, 새 기록을 파일 끝에 한 줄씩 덧붙이는 방식으로 변경 파일 전체를 다시 쓰지 않아서, 기록이 많이 쌓여도 한 건 추가가 전체를 다시 쓰는 방식보다 훨씬 빠름 (캡처의 '1건 추가' 항목)
  • stress_test.py가 main()을 10,000번 실행한 뒤 자동으로 검증 개수 · id 연속 · 중복 · 필수 항목 · 저장 순서 · 올바른 JSON · 실행 속도
  • 웹 리포트에는 최근 30건만 불러와서, 기록이 아무리 쌓여도 리포트 크기는 일정 이유: 기준값을 바꿀 때마다 모든 회차를 다시 채점하므로, 전부 담으면 파일이 커지고 화면이 느려짐. 전체 기록은 파일에 그대로 보관
python stress_test.py 실행 결과 (클릭하면 크게 볼 수 있음)
07. 기록 파일 구조

practice_history.json

[
{"id":1, "timestamp":"2026-11-03 14:20:05", "original":"original.wav", "take":"my_take.wav",
 "tolerance_ms":150, "accuracy":87.5, "missed":2, "extra":1,
 "original_onsets":[0.07, 0.51, ...], "user_onsets":[0.07, 0.55, ...]},
{"id":2, ...},
{"id":3, ...}
]
  • 파일 전체가 항상 올바른 JSON 배열이고, 기록 한 건은 실제 파일에서 정확히 한 줄 (위 내용은 보기 좋게 줄바꿈한 예시)
  • id는 1부터 이어지는 번호 — 누락·중복 여부를 바로 검사할 수 있음
  • original_onsets·user_onsets — 기준값을 바꿔도 이 회차를 다시 채점할 수 있게 하는 원본 데이터
  • 쓰다가 중간에 꺼지거나 일부 줄이 깨져도, 읽을 수 있는 기록은 살리고 복구하도록 처리
08. 검증

점검한 내용

  • 파이썬과 웹페이지의 재채점 결과 일치 — 기록의 모든 회차를 여러 기준값(10~1000ms)에서 양쪽이 각각 계산해 비교 정확도 · 평균 오차 · 놓친/엉뚱한 음 · 구간별 집계까지 모두 동일
  • 기본값 저장 — 페이지에서 바꾼 값이 설정 파일에 저장되고, 새로 접속하거나 다시 실행해도 유지됨 슬라이더를 연달아 움직여도 마지막 값만 저장
  • 잘못된 요청 차단 — 범위를 벗어난 값, 형식 오류, 다른 사이트에서 온 요청은 거부
  • 파일 손상 복구 — 쓰다 끊긴 기록, 빈 파일, 이전 형식 파일을 각각 복구하거나 보관 후 새로 시작
  • 10,000회 반복 실행 — 기록 누락·중복 없이 누적됨 (06번 캡처)
09. 이슈 / 보완할 점

진행하며 발견한 이슈

  • 새로고침하면 옛 기본값으로 열리는 문제 — 리포트 파일에 "만들 당시의 값"이 들어 있어서 발생 해결: 서버에서 열 때마다 최신 기본값을 받아오도록 수정
  • 기록이 늘수록 실행 시간이 늘어남 — 매 실행마다 기록 파일을 한 번 읽어 개수를 세기 때문 (10,000건에서도 1회 1초 이내) 완화: 한 번만 읽도록 정리, 화면에는 최근 30건만 사용 / 개선 방향: 개수를 따로 저장하는 색인 파일
  • 서버 모드에서는 프로그램이 계속 실행됨 — 종료는 Ctrl+C, 서버가 필요 없으면 --no-serve
  • 7주차 이전 형식의 기록은 다시 계산할 수 없음 — 원본 onset이 없어서 보관 파일로 옮기고 새로 시작
  • 동시에 여러 번 실행하는 경우는 고려하지 않음 — 한 사람이 한 번에 하나씩 실행하는 상황을 가정

범위 결정 — 음정(피치) 정확도 분석은 하지 않습니다.
기타는 여러 줄을 동시에 눌러 소리를 내는 코드 연주가 많고, 하모닉스나 반음·풀 벤딩처럼 음정이 애매하게 변하는 기법도 있어서 음정을 안정적으로 판정하기 어렵다고 판단했습니다. 대신 어떤 기법으로 쳐도 "언제 소리가 났는지"는 확인할 수 있으므로, 박자(타이밍) 정확도에 집중해 완성도를 높입니다.
